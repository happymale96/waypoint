# L-Tech Waypoint

Delivery-run planner PWA for L-Tech Automation. Vanilla HTML/CSS/JS — no framework, no build step. Phone-first (400 px), dark mode follows the system. Works under a sub-path (`/waypoint/`): all URLs are relative.

Live: https://happymale96.github.io/waypoint/

## Releases and the build stamp
The service worker's cache name is `waypoint-<stamp>`. The stamp is an 8-character content hash of the whole app shell (html, css, js, json, icons), written by `tools/stamp-sw.js` into `sw.js` (`BUILD`) and `app.js` (`BUILD_STAMP`, shown in **Settings → build …**).

```
node tools/stamp-sw.js          # stamp (run before every commit; idempotent — same files, same stamp)
node tools/stamp-sw.js --check  # exit 1 if the stamp is stale (use in CI or a pre-commit hook)
```
How a release reaches the phone: the page and every `.html/.js/.css/.json` file are fetched **network-first** (bypassing the HTTP cache, so GitHub Pages' 10-minute `max-age` can't serve stale code) and only fall back to the cache when offline; icons are cache-first. A new `sw.js` installs with `skipWaiting()`, deletes old `waypoint-*` caches on activate, `clients.claim()`s the open page, and the page reloads once. The app also calls `registration.update()` on every launch and whenever it returns to the foreground. API calls (TomTom, Google) are never cached. If the reload would interrupt an open sheet or a running plan, it waits until you are done.

## Keys
Paste them in Settings; they live in this phone's localStorage only (never committed, never exported).
- **TomTom** — all travel times from the **Routing API** (`calculateRoute`, one leg per request, live / predicted traffic). The free plan's allowance is **monthly and per API** (Routing 20,000 a month; Matrix Routing 2,500 a month, no longer used by default). See **TomTom on the Routing API** below.
- **Google Places (New)** — place search only, and only when you tap *Search Google*. Saved places are searched locally first. The Settings screen shows a client-side call counter (this device only; no Google-side cap is set yet). One request type: `POST places:searchText`, field mask `places.displayName,places.formattedAddress,places.location` (Text Search **Pro** SKU; all three fields are read).

**Pacing.** TomTom's Routing API allows 5 queries per second, counted on *arrival*, and network latency moves arrivals around: batches of 4 starts spaced exactly 1,000 ms apart can land 8 arrivals inside one second. So the app spreads its starts evenly: at most ONE request start every 300 ms (`Providers.createLimiter`, one limiter in front of `routeLeg`, which every TomTom Routing request uses: the PLAN's table and check legs, the live re-time, the look-ahead after DONE / SKIP, the fuel shortlist; End day sends none). Requests wait in a first-in-first-out queue; results are the same, only later: 12 requests start at 0 / 300 / 600 ... 3,300 ms, 42 requests take 12.3 s to start, so a 3-stop PLAN waits about 5 s and a 6-stop PLAN with nothing learned about 16 s. A 429 is still retried once, no sooner than 1,200 ms after it, back through the same queue (behind whatever already waits); a second 429 behaves as before. While a PLAN fetches a batch of more than 4 requests the PLAN notice reads `Getting travel times N of M…`; the final `Travel times: TomTom Routing — N requests` banner replaces it. The limiter takes its clock and timer as functions (`test/limiter.test.js` runs on a fake clock, no real waiting). The request count (banner = Usage counter = real fetches) is unchanged.

Request (TomTom Routing API v1, `calculateRoute`): `GET https://api.tomtom.com/routing/1/calculateRoute/{lat,lon}:{lat,lon}/json?key=…&travelMode=car&traffic=true&routeType=fastest&routeRepresentation=summaryOnly&computeTravelTimeFor=all&departAt=now|2026-11-24T18:15:00+08:00`. The answer's `routes[0].summary` gives `travelTimeInSeconds` (TomTom's best estimate for that departure: live traffic for now, typical road speeds for the day of the week and time of day for a later departure), `lengthInMeters` and, with `computeTravelTimeFor=all`, `historicTrafficTravelTimeInSeconds` ("time-dependent historic traffic data"): that typical time is what the app learns; today's decisions and ETAs use `travelTimeInSeconds`. An answer without `historicTrafficTravelTimeInSeconds` stores nothing for that pair (the live figure is never stored as typical) and is recorded as such; a failed answer (400 / 403 / 429 / 5xx) is never stored. `departAt` is the Malaysia wall clock with the `+08:00` offset, URL-encoded (`%2B`), computed from UTC whatever the device zone; a time not at least a minute ahead is sent as `now`.

## Solver rules (solver.js)
- One visit per distinct place (merging all pickups, deliveries, errands there), except a First stop place, which may get a second visit (see **First stop** below). Max 12 stops.
- Hard: pickups before their delivery; urgent deliveries before every non-urgent delivery, in `urgentRank` order (a merged stop uses the lowest rank delivered there); with *No detour*, stops that contain no urgent-job action wait until every urgent delivery is done; `arriveBefore` is hard (if nothing fits, the 5 least-late plans are returned with violations named). `arriveAfter` makes you wait at the stop (shown as a wait), it is not a violation.
- Closed windows are `{days:[1..7] (ISO, Mon=1), from, to}` per place, matched against the weekday of the predicted arrival. By default they are advisory (CLOSED badge only). With `respectClosedWindows` an arrival inside a window waits until it ends (the wait counts toward the total; dwell starts after) — the solver reorders when that beats waiting. The Route tab's **Avoid lunch** button runs exactly that on the not-done stops from the cached matrices (no API call) and shows it as an alternative card with the time delta; *Use this* adopts it.
- `Solver.retime(plan, fromStopIndex, nowISO)` re-times the not-done stops of a stored plan (order unchanged, nearest-slice matrices, dwell, waits). The app calls it on DONE/SKIP, on launch and when the app returns to the foreground. A DONE no longer re-fetches the whole matrix (only the 1 x 1 live re-time; see **TomTom budget**).
- The current plan (order, ETAs, done/skipped state, matrices with `fetchedAt`) is stored, so the Route tab survives closing the app and the service-worker reload. *Clear plan* forgets it.
- Objective: minimum elapsed time start → end (drive + dwell + waits). Each leg uses the matrix slice whose `departAt` is nearest the leg's predicted departure.
- Search: DFS with constraint pruning, an admissible lower bound, and a top-5 dominance table; hard time-limit of 1.8 s (returns best found).

## First stop, just collect, missed-window wording (25 Nov 2026)
- **First stop** (add and edit forms, every job and errand; default off; one entry at a time: turning it on for another entry moves it, toast `First stop moved from Office to Carrier`). It pins that entry's first stop (the errand place, its first pickup, or the delivery of a deliver-only job) as the first visit after the start: a hard rule that beats urgent; the urgent rules apply to everything after it as before. At that place everything doable on arrival is done in the first visit (errands, pickups, deliveries of items already with you). A delivery there whose item is collected elsewhere today is a **second visit**: its own stop key `<placeId>#2` (same coordinates, its own Route card with only its tasks, its own REACHED / DONE / SKIP / MSG / auto-reach; 0 s and no request to or from the first visit). Places without a First stop keep the single merged visit. The rule holds for PLAN on a running day and for the re-check after DONE / SKIP while that visit is pending; done or skipped, it has no further effect (a pending second visit keeps its key through re-solves: `job.visit2` on the solver's copies). `FIRST` tag (accent colour) on the Plan card and the first-visit Route card. One day only: End day (and so the carry-forward) clears it. Export carries `firstStop`; an Import without it = off.
- **Just collect**: a job with pickups and an empty "Deliver to" (hint `Just collect — stays with you`). It plans its pickups only (no delivery stop, no ordering rule against any other place). DONE at its last pickup = the job is finished for the day and its item goes into the With you bar (the loose-items store, Dropped off / Deliver to…); it is never carried forward as undone and the item stays in the bar across days. No MSG button (and a supplier place never shows MSG or the after-DONE ETA prompt: suppliers are never messaged). Jobs with a delivery place (also to the Office) are unchanged.
- **Wording**: no message shows a job id. A missed arrive-before reads `Arrive-before missed at Eastern Press: arrives 09:50, must be before 09:30 (Gasket to Eastern Press)`; when the collect-before-deliver rule is the cause (straight there would be on time): `Office arrives 10:07, must be before 09:40 — it has to come after Carrier (Compressor is collected there)`.
- Tests: `test/firststop.test.js` (S1-S8 on the 25 Nov minute table). S1 drives 183 min (O, A, C, E, K, H on that table; the brief's 182 is the order WITHOUT First stop, which starts at Klang).

## After rule, stopped auto-Reached, REACHED / DONE colours, screen on, Cancel job (25 Nov 2026)
- **After** (add and edit forms, every job and errand; optional, empty by default): a multi-select, in the place-picker row style, of the places with an open job or errand today (not this entry's own places). `job.afterPlaces = [placeId]`. This entry's stop (its delivery, else its last pending pickup, else the errand place) comes after the last visit today to each chosen place: a hard "must come before" rule in the solver, like collect-before-deliver; everything else is still ordered for the fastest finish. Priority: First stop > After > urgent (an urgent job with an After rule waits, no banner, its places are not DETOUR). A chosen place with nothing pending (DONE, SKIPPED, cancelled) is satisfied; the rule holds for PLAN on a running day and the re-check after DONE / SKIP. Remove one of the rules.` (one line per impossible group; a cycle drops every After rule in it). Plan card: one small line `after Asian Automotive, Carrier`. One day only: End day (so the carry-forward) clears it. Export carries `afterPlaces`; Import without it = none. Saving an edit shows the existing "tap PLAN" note. Tests: `test/after.test.js` (T1-T8).

## Fuel stop (Route tab → Add fuel stop)
Settings → **Fuel**: brand (default Caltex), fuel stop dwell (7 min), max searches per tap (1–50, default 50). A tap searches Google Places for the brand around sample points every ~4 km along the **whole remaining route** (≤ 5 at a time, every call counted in the daily counter; the daily guard stops at 140 calls a day), keeps results whose name contains the brand, and adds them to a permanent **station memory** (Export/Import JSON; never shown in the Places tab; Settings → *Forget stations*). The 5 stations with the smallest straight-line detour are timed with TomTom (existing lookup + cache) and the one with the fewest extra minutes, at the best of its 2 best legs, is shown in a preview: **Add**, **Next best** (no new search), **Cancel**. Fuel never goes before a pending urgent delivery. Nothing is added without **Add**. A search of the same remaining route under 10 minutes ago is reused (0 Places calls); with no Google key, offline or no budget left the remembered stations are used. One fuel stop per plan (*Change fuel stop* replaces it). It is a normal stop (DONE / SKIP / REMOVE, no WhatsApp); a replan (PLAN on a running day), *No detour* and *Avoid lunch* keep it. In the day log it is a stop with a done time, **not a job**: job counts ignore it and it never carries forward; the summary shows `Fuel: <station> <time>`.

## Reached before Done (Route tab)
Every ordinary stop and the fuel stop has ONE primary button: **REACHED** until you arrive, then **DONE** (same place and size). REACHED only stamps the arrival time (no WhatsApp message, no day-log entry); for 500 ms after it the button ignores taps. The card then shows `Reached 14:10` (`· auto` when it was automatic) with a small **Undo**; Undo returns the button to REACHED and stops auto-reach for that stop for the rest of the plan. Undo of DONE returns to the reached state (reachedAt kept); SKIP works from either state. The end-point card keeps its ARRIVED button.
- **Auto-reach** (Settings → Reached, default on): within 150 m of exactly one pending stop, app open, with a fresh fix (the app's 5-minute origin rule) accurate to 100 m or better, evaluated on every GPS update and when the page becomes visible. Toast `Reached <name> 14:10 (auto) · Undo`. No background work, no new permission.
- **GPS watch** (why auto-reach fires with the app left open): ONE `navigator.geolocation.watchPosition` (high accuracy, maximumAge 10 s, timeout 20 s) runs while the page is visible, a stop is pending (not done, not skipped) and the day is open, and only when location is already allowed (it never prompts). It is cleared when the page is hidden, nothing is pending or the day is closed — never in the background, never two. Every position is stored with its time and auto-reach runs at once; a watch position NEVER calls TomTom: it only re-times locally (at most once per 30 s; an auto-reach re-times at once), counting the ETAs down from the last TomTom-based times (see **TomTom budget**). Back in the foreground: the watch restarts and one fresh fix (maximumAge 0) is requested; auto-reach runs when it arrives, never on a stored fix. Errors never toast: denied / unavailable stop the watch until the next visibility change (the status line says why, as before); a timeout leaves it running.
- **Re-time**: a reached, not-done stop is *on site*: expected departure = max(now, reachedAt + planned dwell), later stops are timed from that; the status line reads `On site at <name> since 14:10`.
- **Travel time from the navigation tap**: the FIRST tap on a stop's own WAZE / MAPS button (or the end point's) after the previous departure is its `navStartedAt` (persisted with the plan, kept through re-solves, cleared on carry-forward). Later taps, and taps after Reached / ARRIVED, change nothing; the whole-route *Open in Google Maps* button never sets it.
- **Time split by the day's timeline** (`Reached.dayTimeline`, not per stop): every tap on a stop's own nav button (and the end point's) is a day event `{type: nav, stopId, at}`; Reached rides on the done event, a skip of a reached stop is a `skip` event. After a departure (day start, a DONE, or the skip of a reached stop) the state is BETWEEN until the first nav tap for ANY stop, then DRIVING until the next arrival at ANY stop (Reached, or done − planned dwell when there is no usable Reached), credited to the stop that ends it; then ON SITE until DONE / SKIP. Taps for other stops while driving, a stop skipped without Reached, added / removed / re-ordered stops and replans change nothing; a tap while on site takes effect at the departure; no tap between a departure and an arrival = all driving, flagged estimated. Days recorded in the previous format (`timeSplitV` 2, one `navStartedAt` per done stop) are converted into nav events when read; days with no Reached data keep the old card. The summary shows ONE driving figure (the four-bucket bar with legend); the Plan-vs-actual section is gone (data kept; only `Replans: N` stays).
- **Day log / summary**: each done event keeps reachedAt, reachedSource, navStartedAt and the planned dwell (raw); ARRIVED keeps the end point's navStartedAt; the day record keeps the real lunch break (`breakStartedAt` / `breakEndedAt`). End day and the day's history show `Driving 2 h 10 min · On site 1 h 47 min · Between stops 38 min` (+ ` · Lunch 52 min` when a break was taken, `(part estimated)` when any stop is) and per stop `left prev 13:40 · nav 13:52 · arr 14:10 · done 14:32` (only the values that exist). Between stops = nav − previous departure (the previous stop's DONE, or the day's start); driving = arrival − nav; on site = DONE − arrival. Without a nav tap: between stops 0, driving = arrival − previous departure, estimated. The break's overlap is taken out of whichever bucket it falls in, so the four never double-count. Days closed before this change (no version mark) keep the old `Driving · On site` card with `arr 14:10 · left 14:32`.
- **Arrivals**: Arrival = reachedAt, except when it is missing or under 60 s before DONE (a double-tap on leaving): then `doneAt − planned dwell`, never before the previous departure, shown as `~14:12`. The final drive counts once the end point was marked ARRIVED. Days with no reachedAt anywhere show the summary as before (nothing is backfilled).

## Lunch break (the driver's)
Settings → **Lunch break**: *Plan a lunch break* (default on), *Available from* (12:15), *Length (minutes)* (60); device-stored, in Export / Import. Not the place form's lunch window — that is the customer's.
- **Assumed break**: while it is neither taken nor skipped, `LunchBreak.applyBreak` adds the length once, at the first departure at or after *Available from* (leaving the current point or a stop); every later stop and the end arrival shift (an arriveAfter wait absorbs what it can). A day that finishes before that time gets nothing. It is applied to every re-timed plan (the app's one timing path after `Solver.retime`), so the Route ETAs, LATE, the end arrival, *Avoid lunch* and the WhatsApp ETA all see it. The solver's order search does not model it (order rules unchanged); the timeline shows `Lunch break ~12:40–13:40` where it sits.
- **The bar** (Route tab, above the stop list, from *Available from* on while a stop is pending): `Start lunch break (1 h)` · `Skip today`. Start: the real break replaces the assumed one — later stops are timed from now + the remaining break; the bar reads `Lunch until 13:20 · End break` and the status line `Lunch break until 13:20` (auto-reach still works). End break (or the length elapsing) ends it; the route re-times from now; one break a day. Skip today removes the assumed break; `Lunch skipped · Undo` stays in the Route header until End day. The state survives reloads (`meta:lunchBreak`, per day).

## Items with you (Plan and Route tabs)
A slim bar near the top of the Plan and Route tabs, **With you: N item(s)**, appears whenever something is with you; tap it to expand the list (row: item, `from <place> · today 14:05`). `OnBoard.onBoard(state, at)` is the one rule: an item is with you when it was collected by a collect -> deliver job whose delivery is not done, when it belongs to an in-hand job whose delivery is not done, or when it is a **loose item**.
- **Loose items**: a collect-only job ("collect X, no delivery") marked DONE leaves one (`{id, item, notes, collectedFrom, collectedAt, sourceJobId, status: with-me | dropped | converted, droppedAt?, droppedPlace?, convertedJobId?}`, collection `loose`, in Export / Import as `looseItems`). Undo of that DONE removes it. A loose item is not a job: job counts never change, and End day does not clear it.
- **Dropped off** (loose rows): status dropped + the time; a fresh GPS fix (never prompts) within 150 m of a saved place stores that place's name; toast `Dropped off: <item> · Undo`; logged as a day event (`dropoff`, `undo of dropoff`). **Deliver to…** opens the add-job form in in-hand mode (item and notes filled in, focus on the destination); saving converts the loose item into that job (`job.looseId`) which tracks it from then on; cancelling changes nothing. If that job is deleted or dropped at End day the item is with you again. Rows of a pending delivery job have no buttons: `-> <destination>`.
- **Summary**: STILL WITH YOU = the day's own rows + the loose items with you at the day's close (closed days are re-rendered with the same rule); under it `Dropped off: <item> 18:05 (<place>)` for items dropped that day. The WhatsApp summary carries both; the CSV columns are unchanged.
- **Backfill** (once, `meta:looseBackfill`): collect-only jobs done today or on the most recent closed day get their loose item (found through the job list and the day log rows); nothing older.

## Dwell migration and the customer message time
- **One-time migration** (`Geo.migrateDwell`, flag `meta/migrations.dwell2026_11_23`): the first time a build with it loads on a device, every supplier place gets dwell 10 and every customer factory (stored type `factory`) 30; office, home and other are untouched. Settings: default dwell supplier 10, customer factory 30; ETA padding 10. One toast says how many places changed. A plan in progress takes the new dwell for its not-done stops at the next re-time (order kept). The code defaults match, so a fresh install gets the same values; an Import of data without `dwellMigrated` runs the same migration (exports now carry `dwellMigrated: true`).
- **Message time** (`Messages.messageMinutes`): ETA + padding minutes, rounded up to the next 5-minute mark only if not already on one; nothing else is added (17:00 with padding 10 -> 17:10, 17:02 -> 17:15). The message shows it in the app's 12-hour format (`5:10 petang` / `5:10 pm`).

## PLAN on a running day (there is no "Replan from here" button)
A day is **running** when a plan exists, its day is not closed, and a stop is done, reached or skipped, or a navigation tap has been made (`OnBoard.isDayRunning`). Then **PLAN** is the old *Replan from here*: it re-solves the stops that are not done (plus new jobs) with fresh TomTom times, keeps the done stops, the reached / navigation state, the fuel stop, the lunch state and the replan count, and starts from the live position, now. Each time the Plan tab opens on a running day the start chip resets to *My location* and the time chip to *Now*; a chip changed on purpose before tapping PLAN is used. A **skipped** stop stays skipped through PLAN (not re-solved, no ETA, its job not added again; `OnBoard.jobsForPlan`); only *Undo skip* brings it back, and the next PLAN then includes it. A skipped job is still not done, so End day carries it forward. Before the day is running PLAN plans afresh, exactly as before. The Route tab row is `Open in Google Maps` | `Add fuel stop`.

## Edit a job (Plan tab)
A pending or held job opens in the Add job form in **EDIT mode** (title *Edit job*, button *Save changes*, every field pre-filled) when you tap either box of its card (COLLECT / IN HAND, DELIVER, ERRAND) or the pencil in the button row (**Urgent | pencil | hold | delete**). Cancel changes nothing. Saving updates the SAME job (`JobEdit.updateJob`): same id, same position in the list, still held if it was held, the loose-item link and the carry-forward history kept. A pickup already collected is shown read-only (*Collected 11:02 - cannot change*) and can't be changed; the pending part, item, notes, urgent and the time rules can. A job with a done part can't become an errand; a fully done job is not editable. Validation is the one Add job uses (`JobEdit.validate`): required fields, an item with no place, and **pickup and delivery cannot be the same place**.
- **After planning**: before this change the app showed nothing when a job was added, deleted or changed after a plan existed (the route simply stayed as planned until PLAN). Saving an edit now sets one slim line on the Plan and Route tabs, *Jobs changed - tap PLAN to update the route*, kept with the stored plan (it survives a reload) and cleared by the next PLAN. The route itself never changes until PLAN is tapped. Adding and deleting jobs behave as before (no line).

## Pinned places
Each saved place has a boolean `pinned` (place form: **Pin to top of search**; Export / Import carry it). In every place picker (the job form, the start and end chips, Add place) pinned places are listed first in name order with a small pin glyph, both with an empty box and while typing (they stay on top even when they don't match; the normal matches follow without repeating them; a Google search is still started only when no saved place matches the text). The Places tab sorts pinned first, then the existing name order. **One-time migration** (`Geo.migratePins`, flag `meta/migrations.pinOffice2026_11_24`, no toast): every saved place of type *office* is pinned, nothing else; exports carry `pinMigrated: true` and an Import of data without it runs the same migration.

## Route tab after End day
When today's day record is closed and no PLAN has been made since, the Route tab shows one card, **Day closed 17:59** with **View summary** (the With you bar stays above it while something is with you): no times, no stops, no End day, no fuel button, no location request. Planning again shows the normal Route tab.

## First use
1. Open the live URL on the phone (Chrome / Safari).
2. Settings → paste the TomTom key (and the Google key if you want Google place search).
3. Menu → *Add to Home Screen* / *Install app*.
4. Places → check Home and Office; add suppliers/factories (+ WhatsApp number, closed windows).
5. Plan → *Add job*: pickups (place + item), delivery, urgent / time window — or *Errand*.
6. Pick start (My location / a place), end (default Home), depart time (blank = now).
7. Tap **PLAN**. Route tab shows the timeline; *No detour* re-solves instantly.
8. Per stop: **WAZE** to navigate, **MSG** for a WhatsApp ETA, **DONE** when finished (offers to message the next delivery).
9. If plans change: **SKIP**, then open the Plan tab and tap **PLAN** (see *PLAN on a running day*).
10. Settings → Export JSON for a backup.

## ETAs from your location
On opening the Route tab, returning to the app, and after DONE (at most once per 2 minutes, skipped if you moved under 300 m), the app takes a geolocation fix **only if permission is already granted** (high accuracy, 5 s; accuracy worse than 200 m is ignored). With a good fix it makes ONE TomTom Matrix request (you → next stop, live traffic) and re-times the stops via `Solver.retime(plan, from, now, {durationToNextSec})`: first ETA = now + that duration, later ETAs follow through the existing legs and dwell times; order never changes. Within 150 m of the next stop it counts as arrived (no request). CLOSED / LATE flags and the Avoid-lunch delta follow the new times. The Route tab says "Times from your location, HH:MM" or "Times from plan start" (no fix, denied, offline, provider error).

## Route tab: what the header and status line mean
- Header = the current re-timed plan: stops left (not done, not skipped), time left to the re-timed end arrival, the end arrival, "Departed HH:MM" (original depart). The Route tab re-renders once a minute (no network call); no stop or end time is ever shown in the past (a past ETA becomes now and later times shift with it).
- Status line (tap = retry now, bypassing the 2-min / 300 m throttle): "Times from your location, HH:MM", "Times from last DONE, HH:MM" or "Times from plan start"; without a live fix it adds why: location not allowed / no GPS fix / routing failed / offline. A live origin older than 5 min is never reused.
- Fix rules (everywhere): high accuracy, 10 s timeout, maximumAge 60 s; on timeout one retry at low accuracy, 5 s. Route ETAs accept 200 m or better.
- SKIP is an explicit tap only; a skipped stop is greyed, has no ETA, is out of the chain and the counts, and has **Undo skip**.
- The end point is a card (**WAZE**, **ARRIVED**). ARRIVED writes `arrived_end` to the day log (Finished = that time unless edited; the summary adds the last-stop -> end-point leg), shows "Day complete - view summary" and never closes the day. **End day** is also at the bottom of the Route tab.

## Manual places
In any place picker the last row is **Can't find it? Add manually** (always, also offline / on a failed search): name, type, salutation / language, location from **Use where I am now** or pasted coordinates / a long Google Maps link (short links can't be read), optional address note. Saved with `source: "manual"`; zero Google Places or routing requests. In the place editor, **Update location to where I am now** moves a wrong pin (the old one is kept as `previousLocation` for one undo).

## TomTom on the Routing API (24 Nov: Matrix Routing's monthly 2,500 used up)
TomTom's free allowance is **monthly and per API**: Matrix Routing 2,500 / month (used up), Routing API 20,000 / month. There is **no daily reset**. The app builds every travel time from Routing API requests (one origin -> one destination each), learns typical times, and spends as few requests as it can (`traveltimes.js`, `budget.js`, `providers.js`).
- **Learned travel times**: per (from place, to place, part of the day) the 5 most recent samples, value = the median. Parts of the day (Malaysia time): AM peak 06:30-09:30 · Day 09:30-16:30 · PM peak 16:30-20:00 · Night 20:00-06:30. A sample is any TomTom answer between two saved places (a point within 150 m of a saved place counts as that place), stored under the bucket of its departure, with TomTom's typical (historic) time when the answer carries one, so a jam on the day does not enter the memory. Never your own driven times. In Export / Import; Settings -> *Travel times* shows "Learned travel times: N pairs" and **Forget**. **One-time clear** (`TravelTimes.runLearnedClearOnce`, flag `meta/migrations.learnedClear2026_11_24`): build 03077b48 stored the live figure when an answer had no typical time; fa101395 stores only the typical figure but its samples look the same and it purged nothing, so the first load of this build clears every learned sample once (the "last typical time" line is kept; places, jobs, days and counters are not touched); samples saved afterwards are kept. Exports carry `learnedCleared: true`; an Import of an older export clears its samples the same way. Settings -> Travel times shows `Learned: N pairs · last typical time from TomTom: today HH:MM | 23 Nov | none yet` (+ ` · last reply had no typical time` when the most recent answer had none).
- **Only useful pairs are fetched**: never a place to itself, nothing TO the start, nothing FROM the end, start -> end only with no stops, never a delivery -> its own pending pickup. n stops = n + n(n-1) + n pairs.
- **PLAN, more than 5 stops**: the table for the bucket holding the midpoint of the day (start + dwells + 3 h): learned value, else the same pair in another bucket (0 requests), else fetched at the middle of that bucket (or now, when now is inside it). The existing solver orders the stops (rules unchanged). Then the chosen order is **checked**: one request per leg at that leg's planned departure (dwell, lunch break, windows included) = stops + 1 requests. Checked total more than 15% off the table: the checked times go into the table and it is solved once more (a changed order is checked once). At most two solves and two checks. The ETAs come from the checked legs.
- **PLAN, 5 stops or fewer**: every needed pair live for the departure (3 stops = 12 requests), no check pass.
- **Requests per PLAN** (`TravelTimes.planSession`, from the PLAN tap to the end of the Route tab's first re-time): the banner number is every request the PLAN sent, so it always equals the Usage counter's rise and the real fetches. Before this, the banner counted legs, not requests: a 429 and its one retry are two requests (both counted by the Usage counter, as TomTom sees them), and the Route tab's first re-time (a start that is a saved place) came after the banner; on the phone 12 legs showed as 12 while the counter rose by 19 (7 legs answered 429 first, then retried). A request identical to one the PLAN already sent (same from, to and departAt as sent) is answered from memory: the 6-stop check's first leg (from the start, now) is the table's own request (49 -> 48); anything with a different departAt or origin is still fetched. Count, N stops (needed pairs P = N + N(N-1) + N, minus a delivery -> its own pending pickup; L = pairs learned): N <= 5: P, + 1 when the start is a saved place and your fix is elsewhere (the first re-time from where you are); N > 5: (P - L) + (N + 1 - 1 when the table's start -> first stop was fetched for now) + a second check only when the order changed; every 429 retry adds 1 (shown). A learned sample is saved at most once per pair per PLAN, TomTom's historic figure only.
- **After each stop** (Settings: *Switch automatically* (default) | *Ask me* | *Off*): DONE or SKIP with 2 or more stops pending looks for a faster order with live times for now from where you are. More than 5 pending: a first-leg probe (one request to each stop that may come next); 5 or fewer: every needed pair (5 pending = 30 requests). The pending stops are re-solved with every rule; a switch needs a different best order that reaches the end point at least 10 minutes earlier. Automatic: the order changes, the notice "Order updated: next is X (was Y) - saves about N min · Undo" stays until the next tap on a stop button; Undo restores the previous order exactly. *Ask me*: the same line as a card with Switch / Keep mine. A stop already messaged today stays next unless you choose Switch ("X was already messaged"). Every applied switch is a replan in the day log. It never adds, removes, skips or un-skips a stop. Reached never triggers it.
- **Live re-time triggers** (`Budget.retimeDecision`, unchanged): GPS-watch positions never call TomTom. One request (current position -> next pending stop) on PLAN (unless the plan's first leg was just fetched live from where you are), Undo and a tap on the status line (always); when the page becomes visible again and every 10 minutes while visible with a stop pending (5-minute gap); fuel added / removed. DONE / SKIP use the look-ahead above (or this single re-time when it is off, paused or TomTom is out).
- **Fuel stop**: the Google Places search is unchanged; every (station, position in the route) is ranked with the estimator, real times are fetched for the best 8 only (2 requests each, 16 at most) and the existing lowest-detour rule chooses among them.
- **End day km**: the metres already held for the legs driven (and the learned distances); no new request. Each DONE / ARRIVED holds the leg just driven from, in order, the plan's matrices, the previous plan's legs carried across a PLAN on a running day (`ctx.carryLegs`), the learned memory. Before this, a PLAN on a running day from a live position left the next leg unheld (the done stop is not in the new plan), and the End-day fill needed a learned value for EVERY leg (held ones and a GPS start included) and only counted for that exact sequence, so the day closed with km blank ("km —", "day(s) without km") and a later stop the same date dropped the fill; now only the missing legs are filled, per pair, into the day's legs. Days already stored are left as they are: their missing leg is not in their own data (an older `routed` fill is read per pair, no write).
- **Usage** (Settings): `TomTom Routing   D today · M this month of 20,000` and `Google Places    D today · M this month  (daily guard 140)`, a thin bar each; Matrix only once it is above 0. Counted on this device (every response that came back), per Malaysia day and per UTC month; in Export / Import. Google Places today and this month come from ONE record (`settings.usage.places`, bumped like TomTom); a one-time repair (flag `meta/migrations.placesMonth2026_11_24`) raised this month to today where the old separate "today" counter (`placesCallsToday`, now removed) was higher. The allowance is editable. From **90%** of it the automatic re-times (10-minute, on-visible) and the after-stop look-ahead pause for the rest of the month and the Route tab shows `TomTom allowance nearly used - live times paused, PLAN still works`; PLAN and tapped re-times continue, and DONE falls back to one next-stop re-time.
- **When TomTom cannot answer** (401 / 403 / 429 after its one retry / 5xx / no connection): ONE notice on the Plan and Route tabs naming what happened, no raw HTTP text: 403 `TomTom refused the key or the monthly allowance is used up - using estimated times`, 429 `TomTom is busy (too many requests) - using estimated times`, otherwise `TomTom unavailable or monthly allowance used up - using estimated times`. A 400 (no route for a leg) is not "down": the other legs are still fetched, that pair uses an estimate and the notice reads `TomTom could not route a leg - using estimated times for it`. Estimate = straight-line km x 1.3 at 25 km/h (under 5 km), 40 km/h (5-30 km) or 75 km/h (over 30 km). The ORDER is never mixed: if any needed pair has no real time (fetched or learned, any bucket), the order uses estimates for all pairs and the Route header reads **Estimated order - TomTom unavailable**; card ETAs still use real times where they exist and read `est.` only where they do not. No look-ahead while TomTom is out.
- **TomTom service** (Settings): *Routing* (default; a one-time migration set it on every device) | *Matrix* (the old 3-slice Matrix Routing v2 path, kept for later).

## Messages, contact name, auto-reach
