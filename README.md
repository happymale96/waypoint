# L-Tech Waypoint

Delivery-run planner PWA for L-Tech Automation. Vanilla HTML/CSS/JS — no framework, no build step. Phone-first (400 px), dark mode follows the system. Works under a sub-path (`/waypoint/`): all URLs are relative.

Live: https://happymale96.github.io/waypoint/

## Releases and the build stamp
The service worker's cache name is `waypoint-<stamp>`. The stamp is an 8-character content hash of the whole app shell (html, css, js, json, icons), written by `tools/stamp-sw.js` into `sw.js` (`BUILD`) and `app.js` (`BUILD_STAMP`, shown in **Settings → build …**).

```
node tools/stamp-sw.js          # stamp (run before every commit; idempotent — same files, same stamp)
node tools/stamp-sw.js --check  # exit 1 if the stamp is stale (use in CI or a pre-commit hook)
```
How a release reaches the phone: the page and every `.html/.js/.css/.json` file are fetched **network-first** (bypassing the HTTP cache, so GitHub Pages' 10-minute `max-age` can't serve stale code) and only fall back to the cache when offline; icons are cache-first. A new `sw.js` installs with `skipWaiting()`, deletes old `waypoint-*` caches on activate, `clients.claim()`s the open page, and the page reloads once. The app also calls `registration.update()` on every launch and whenever it returns to the foreground. API calls (TomTom, Google) are never cached. If the reload would interrupt an open sheet or a running plan, it waits until you are done.

## Keys
Paste them in Settings; they live in this phone's localStorage only (never committed, never exported).
- **TomTom** — all travel times (Matrix Routing v2, live traffic). 3 calls per plan (depart, +2 h, +4 h); results are cached in memory for the session, so the *No detour* toggle re-solves with zero API calls. A replan (PLAN on a running day) forces fresh calls.
- **Google Places (New)** — place search only, and only when you tap *Search Google*. Saved places are searched locally first. The Settings screen shows a client-side call counter (this device only; no Google-side cap is set yet). One request type: `POST places:searchText`, field mask `places.displayName,places.formattedAddress,places.location` (Text Search **Pro** SKU; all three fields are read).

TomTom's current docs list `routeSummary.travelTimeInSeconds` (and `trafficDelayInSeconds`) in the response; `noTrafficTravelTimeInSeconds` is not documented, so it is only used as a fallback if present. `departAt` must be `now` or a future time; the first slice uses `now` when departing immediately.

## Solver rules (solver.js)
- One visit per distinct place (merging all pickups, deliveries, errands there). Max 12 places.
- Hard: pickups before their delivery; urgent deliveries before every non-urgent delivery, in `urgentRank` order (a merged stop uses the lowest rank delivered there); with *No detour*, stops that contain no urgent-job action wait until every urgent delivery is done; `arriveBefore` is hard (if nothing fits, the 5 least-late plans are returned with violations named). `arriveAfter` makes you wait at the stop (shown as a wait), it is not a violation.
- Closed windows are `{days:[1..7] (ISO, Mon=1), from, to}` per place, matched against the weekday of the predicted arrival. By default they are advisory (CLOSED badge only). With `respectClosedWindows` an arrival inside a window waits until it ends (the wait counts toward the total; dwell starts after) — the solver reorders when that beats waiting. The Route tab's **Avoid lunch** button runs exactly that on the not-done stops from the cached matrices (no API call) and shows it as an alternative card with the time delta; *Use this* adopts it.
- `Solver.retime(plan, fromStopIndex, nowISO)` re-times the not-done stops of a stored plan (order unchanged, nearest-slice matrices, dwell, waits). The app calls it on DONE/SKIP, on launch and when the app returns to the foreground. Travel times older than 30 min are re-fetched at a DONE.
- The current plan (order, ETAs, done/skipped state, matrices with `fetchedAt`) is stored, so the Route tab survives closing the app and the service-worker reload. *Clear plan* forgets it.
- Objective: minimum elapsed time start → end (drive + dwell + waits). Each leg uses the matrix slice whose `departAt` is nearest the leg's predicted departure.
- Search: DFS with constraint pruning, an admissible lower bound, and a top-5 dominance table; hard time-limit of 1.8 s (returns best found).

## Fuel stop (Route tab → Add fuel stop)
Settings → **Fuel**: brand (default Caltex), fuel stop dwell (7 min), max searches per tap (1–50, default 50). A tap searches Google Places for the brand around sample points every ~4 km along the **whole remaining route** (≤ 5 at a time, every call counted in the daily counter; the daily guard stops at 140 calls a day), keeps results whose name contains the brand, and adds them to a permanent **station memory** (Export/Import JSON; never shown in the Places tab; Settings → *Forget stations*). The 5 stations with the smallest straight-line detour are timed with TomTom (existing lookup + cache) and the one with the fewest extra minutes, at the best of its 2 best legs, is shown in a preview: **Add**, **Next best** (no new search), **Cancel**. Fuel never goes before a pending urgent delivery. Nothing is added without **Add**. A search of the same remaining route under 10 minutes ago is reused (0 Places calls); with no Google key, offline or no budget left the remembered stations are used. One fuel stop per plan (*Change fuel stop* replaces it). It is a normal stop (DONE / SKIP / REMOVE, no WhatsApp); a replan (PLAN on a running day), *No detour* and *Avoid lunch* keep it. In the day log it is a stop with a done time, **not a job**: job counts ignore it and it never carries forward; the summary shows `Fuel: <station> <time>`.

## Reached before Done (Route tab)
Every ordinary stop and the fuel stop has ONE primary button: **REACHED** until you arrive, then **DONE** (same place and size). REACHED only stamps the arrival time (no WhatsApp message, no day-log entry); for 500 ms after it the button ignores taps. The card then shows `Reached 14:10` (`· auto` when it was automatic) with a small **Undo**; Undo returns the button to REACHED and stops auto-reach for that stop for the rest of the plan. Undo of DONE returns to the reached state (reachedAt kept); SKIP works from either state. The end-point card keeps its ARRIVED button.
- **Auto-reach** (Settings → Reached, default on): within 150 m of exactly one pending stop, app open, with a fresh fix (the app's 5-minute origin rule) accurate to 100 m or better, evaluated on every GPS update and when the page becomes visible. Toast `Reached <name> 14:10 (auto) · Undo`. No background work, no new permission.
- **GPS watch** (why auto-reach fires with the app left open): ONE `navigator.geolocation.watchPosition` (high accuracy, maximumAge 10 s, timeout 20 s) runs while the page is visible, a stop is pending (not done, not skipped) and the day is open, and only when location is already allowed (it never prompts). It is cleared when the page is hidden, nothing is pending or the day is closed — never in the background, never two. Every position goes through the same path as any fix (stored with its time, auto-reach at once, the live-origin refresh with its own 2-min / 300 m throttle); local re-timing from watch updates is throttled to once per 30 s (an auto-reach re-times at once). Back in the foreground: the watch restarts and one fresh fix (maximumAge 0) is requested; auto-reach runs when it arrives, never on a stored fix. Errors never toast: denied / unavailable stop the watch until the next visibility change (the status line says why, as before); a timeout leaves it running.
- **Re-time**: a reached, not-done stop is *on site*: expected departure = max(now, reachedAt + planned dwell), later stops are timed from that; the status line reads `On site at <name> since 14:10`.
- **Travel time from the navigation tap**: the FIRST tap on a stop's own WAZE / MAPS button (or the end point's) after the previous departure is its `navStartedAt` (persisted with the plan, kept through re-solves, cleared on carry-forward). Later taps, and taps after Reached / ARRIVED, change nothing; the whole-route *Open in Google Maps* button never sets it.
- **Time split by the day's timeline** (`Reached.dayTimeline`, not per stop): every tap on a stop's own nav button (and the end point's) is a day event `{type: nav, stopId, at}`; Reached rides on the done event, a skip of a reached stop is a `skip` event. After a departure (day start, a DONE, or the skip of a reached stop) the state is BETWEEN until the first nav tap for ANY stop, then DRIVING until the next arrival at ANY stop (Reached, or done − planned dwell when there is no usable Reached), credited to the stop that ends it; then ON SITE until DONE / SKIP. Taps for other stops while driving, a stop skipped without Reached, added / removed / re-ordered stops and replans change nothing; a tap while on site takes effect at the departure; no tap between a departure and an arrival = all driving, flagged estimated. Days recorded in the previous format (`timeSplitV` 2, one `navStartedAt` per done stop) are converted into nav events when read; days with no Reached data keep the old card. The summary shows ONE driving figure (the four-bucket bar with legend); the Plan-vs-actual section is gone (data kept; only `Replans: N` stays).
- **Day log / summary**: each done event keeps reachedAt, reachedSource, navStartedAt and the planned dwell (raw); ARRIVED keeps the end point's navStartedAt; the day record keeps the real lunch break (`breakStartedAt` / `breakEndedAt`). End day and the day's history show `Driving 2 h 10 min · On site 1 h 47 min · Between stops 38 min` (+ ` · Lunch 52 min` when a break was taken, `(part estimated)` when any stop is) and per stop `left prev 13:40 · nav 13:52 · arr 14:10 · done 14:32` (only the values that exist). Between stops = nav − previous departure (the previous stop's DONE, or the day's start); driving = arrival − nav; on site = DONE − arrival. Without a nav tap: between stops 0, driving = arrival − previous departure, estimated. The break's overlap is taken out of whichever bucket it falls in, so the four never double-count. Days closed before this change (no version mark) keep the old `Driving · On site` card with `arr 14:10 · left 14:32`.
- **Arrivals**: Arrival = reachedAt, except when it is missing or under 60 s before DONE (a double-tap on leaving): then `doneAt − planned dwell`, never before the previous departure, shown as `~14:12`. The final drive counts once the end point was marked ARRIVED. Days with no reachedAt anywhere show the summary as before (nothing is backfilled).

## Lunch break (the driver's)
Settings → **Lunch break**: *Plan a lunch break* (default on), *Available from* (12:15), *Length (minutes)* (60); device-stored, in Export / Import. Not the place form's lunch window — that is the customer's.
- **Assumed break**: while it is neither taken nor skipped, `LunchBreak.applyBreak` adds the length once, at the first departure at or after *Available from* (leaving the current point or a stop); every later stop and the end arrival shift (an arriveAfter wait absorbs what it can). A day that finishes before that time gets nothing. It is applied to every re-timed plan (the app's one timing path after `Solver.retime`), so the Route ETAs, LATE, the end arrival, *Avoid lunch* and the WhatsApp ETA all see it. The solver's order search does not model it (order rules unchanged); the timeline shows `Lunch break ~12:40–13:40` where it sits.
- **The bar** (Route tab, above the stop list, from *Available from* on while a stop is pending): `Start lunch break (1 h)` · `Skip today`. Start: the real break replaces the assumed one — later stops are timed from now + the remaining break; the bar reads `Lunch until 13:20 · End break` and the status line `Lunch break until 13:20` (auto-reach still works). End break (or the length elapsing) ends it; the route re-times from now; one break a day. Skip today removes the assumed break; `Lunch skipped · Undo` stays in the Route header until End day. The state survives reloads (`meta:lunchBreak`, per day).

## Items with you (Plan and Route tabs)
A slim bar near the top of the Plan and Route tabs, **With you: N item(s)**, appears whenever something is with you; tap it to expand the list (row: item, `from <place> · today 14:05`). `OnBoard.onBoard(state, at)` is the one rule: an item is with you when it was collected by a collect -> deliver job whose delivery is not done, when it belongs to an in-hand job whose delivery is not done, or when it is a **loose item**.
- **Loose items**: a collect-only job ("collect X, no delivery") marked DONE leaves one (`{id, item, notes, collectedFrom, collectedAt, sourceJobId, status: with-me | dropped | converted, droppedAt?, droppedPlace?, convertedJobId?}`, collection `loose`, in Export / Import as `looseItems`). Undo of that DONE removes it. A loose item is not a job: job counts never change, and End day does not clear it.
- **Dropped off** (loose rows): status dropped + the time; a fresh GPS fix (never prompts) within 150 m of a saved place stores that place's name; toast `Dropped off: <item> · Undo`; logged as a day event (`dropoff`, `undo of dropoff`). **Deliver to…** opens the add-job form in in-hand mode (item and notes filled in, focus on the destination); saving converts the loose item into that job (`job.looseId`) which tracks it from then on; cancelling changes nothing. If that job is deleted or dropped at End day the item is with you again. Rows of a pending delivery job have no buttons: `-> <destination>`.
- **Summary**: STILL WITH YOU = the day's own rows + the loose items with you at the day's close (closed days are re-rendered with the same rule); under it `Dropped off: <item> 18:05 (<place>)` for items dropped that day. The WhatsApp summary carries both; the CSV columns are unchanged.
- **Backfill** (once, `meta:looseBackfill`): collect-only jobs done today or on the most recent closed day get their loose item (found through the job list and the day log rows); nothing older.

## PLAN on a running day (there is no "Replan from here" button)
A day is **running** when a plan exists, its day is not closed, and a stop is done, reached or skipped, or a navigation tap has been made (`OnBoard.isDayRunning`). Then **PLAN** is the old *Replan from here*: it re-solves the stops that are not done (plus new jobs) with fresh TomTom times, keeps the done stops, the reached / navigation state, the fuel stop, the lunch state and the replan count, and starts from the live position, now. Each time the Plan tab opens on a running day the start chip resets to *My location* and the time chip to *Now*; a chip changed on purpose before tapping PLAN is used. A **skipped** stop stays skipped through PLAN (not re-solved, no ETA, its job not added again; `OnBoard.jobsForPlan`); only *Undo skip* brings it back, and the next PLAN then includes it. A skipped job is still not done, so End day carries it forward. Before the day is running PLAN plans afresh, exactly as before. The Route tab row is `Open in Google Maps` | `Add fuel stop`.

## Route tab after End day
When today's day record is closed and no PLAN has been made since, the Route tab shows one card, **Day closed 17:59** with **View summary** (the With you bar stays above it while something is with you): no times, no stops, no End day, no fuel button, no location request. Planning again shows the normal Route tab.

## First use
1. Open the live URL on the phone (Chrome / Safari).
2. Settings → paste the TomTom key (and the Google key if you want Google place search).
3. Menu → *Add to Home Screen* / *Install app*.
4. Places → check Home and Office; add suppliers/factories (+ WhatsApp number, closed windows).
5. Plan → *Add job*: pickups (place + item), delivery, urgent / time window — or *Errand*.
6. Pick start (My location / a place), end (default Home), depart time (blank = now).
7. Tap **PLAN**. Route tab shows the timeline; *No detour* re-solves instantly.
8. Per stop: **WAZE** to navigate, **MSG** for a WhatsApp ETA, **DONE** when finished (offers to message the next delivery).
9. If plans change: **SKIP**, then open the Plan tab and tap **PLAN** (see *PLAN on a running day*).
10. Settings → Export JSON for a backup.

## ETAs from your location
On opening the Route tab, returning to the app, and after DONE (at most once per 2 minutes, skipped if you moved under 300 m), the app takes a geolocation fix **only if permission is already granted** (high accuracy, 5 s; accuracy worse than 200 m is ignored). With a good fix it makes ONE TomTom Matrix request (you → next stop, live traffic) and re-times the stops via `Solver.retime(plan, from, now, {durationToNextSec})`: first ETA = now + that duration, later ETAs follow through the existing legs and dwell times; order never changes. Within 150 m of the next stop it counts as arrived (no request). CLOSED / LATE flags and the Avoid-lunch delta follow the new times. The Route tab says "Times from your location, HH:MM" or "Times from plan start" (no fix, denied, offline, provider error).

## Route tab: what the header and status line mean
- Header = the current re-timed plan: stops left (not done, not skipped), time left to the re-timed end arrival, the end arrival, "Departed HH:MM" (original depart). The Route tab re-renders once a minute (no network call); no stop or end time is ever shown in the past (a past ETA becomes now and later times shift with it).
- Status line (tap = retry now, bypassing the 2-min / 300 m throttle): "Times from your location, HH:MM", "Times from last DONE, HH:MM" or "Times from plan start"; without a live fix it adds why: location not allowed / no GPS fix / routing failed / offline. A live origin older than 5 min is never reused.
- Fix rules (everywhere): high accuracy, 10 s timeout, maximumAge 60 s; on timeout one retry at low accuracy, 5 s. Route ETAs accept 200 m or better.
- SKIP is an explicit tap only; a skipped stop is greyed, has no ETA, is out of the chain and the counts, and has **Undo skip**.
- The end point is a card (**WAZE**, **ARRIVED**). ARRIVED writes `arrived_end` to the day log (Finished = that time unless edited; the summary adds the last-stop -> end-point leg), shows "Day complete - view summary" and never closes the day. **End day** is also at the bottom of the Route tab.

## Manual places
In any place picker the last row is **Can't find it? Add manually** (always, also offline / on a failed search): name, type, salutation / language, location from **Use where I am now** or pasted coordinates / a long Google Maps link (short links can't be read), optional address note. Saved with `source: "manual"`; zero Google Places or routing requests. In the place editor, **Update location to where I am now** moves a wrong pin (the old one is kept as `previousLocation` for one undo).
